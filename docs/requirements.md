# svodka — Requirements

## 1. Назначение

`svodka` — Telegram-userbot, который под **личным аккаунтом** пользователя раз в день
читает указанные чаты, делает саммари сообщений за сутки через LLM и публикует
дайджест в отдельный чат/группу.

Проект задуман как **публичный GitHub-шаблон**: любой человек создаёт из него свою
**приватную** копию и разворачивает себе такой же сервис без собственной
инфраструктуры — всё работает в GitHub Actions по расписанию.

## 2. Роли

- **Maintainer** — владелец публичного template-репозитория (мы).
- **Deployer** — пользователь, который из шаблона делает свой приватный инстанс и
  настраивает его под себя. Может быть неопытным: настройка должна идти через UI.

## 3. Функциональные требования

### 3.1 Сбор сообщений
- FR-1. Читать историю из списка чатов-источников (`source_chats`).
- FR-2. Источник задаётся как `@username` или ссылка `t.me/...`; для приватных чатов
  без юзернейма — по числовому id (фолбэк-резолв через список диалогов).
- FR-3. Собирать только сообщения за окно `window_hours` (по умолчанию 24 ч),
  отсечка по дате сообщения.
- FR-4. Нормализовать сообщение: автор (отображаемое имя), время, текст; медиа без
  текста помечать плейсхолдером (`[photo]`, `[video]`, `[file]` и т.п.); сервисные
  сообщения пропускать.

### 3.2 Саммаризация
- FR-5. Генерировать саммари через LLM. Первый и единственный провайдер — **Claude**
  (Anthropic Messages API).
- FR-6. Провайдер скрыт за интерфейсом `llm.Provider`, чтобы позже добавить других
  (OpenAI и пр.) без изменения остального кода.
- FR-7. При большом объёме применять map-reduce: саммари по каждому чату → финальная
  склейка, чтобы не упираться в лимит контекста/токенов.
- FR-8. Язык вывода настраивается (`output_lang`, по умолчанию `ru`).
- FR-9. Структура дайджеста: по чатам → ключевые темы, решения, упоминания
  пользователя, важные ссылки.

### 3.3 Публикация
- FR-10. Отправлять дайджест в `target_chat`.
- FR-11. **Безопасный дефолт**: `target_chat: me` → публикация в «Saved Messages»
  (предпросмотр). Реальная группа в `target_chat` → «боевой» режим. Отдельного
  булева флага dry-run нет.
- FR-12. Длинный дайджест (> 4096 символов) разбивать на несколько сообщений.

### 3.4 Аутентификация / session
- FR-13. Работа под пользователем через MTProto (`gotd/td`), не Bot API.
- FR-14. Одноразовый интерактивный логин (телефон → код → 2FA) генерирует session.
- FR-15. Логин выполняется в **GitHub Codespaces** (браузерный терминал) командой
  `go run ./api/cmd/login`; результат пишется в Secret (`gh secret set`) с фолбэком
  на ручную вставку, если нет прав.
- FR-16. В рабочем прогоне session берётся из секрета (read-only), повторный логин
  не требуется.

### 3.5 Запуск / конфигурация
- FR-17. Ежедневный запуск через GitHub Actions `schedule` (cron).
- FR-18. Кнопка ручного запуска `workflow_dispatch` для теста.
- FR-19. Секреты — через GitHub Actions Secrets (env). Content-настройки — через
  `config.yml`, редактируемый в веб-UI.
- FR-20. Понятные ошибки при отсутствии конфигурации (нет session/ключей/чатов).

## 4. Нефункциональные требования

- NFR-1 (Стоимость). Хостинг бесплатный (GitHub Actions free tier; задача ~2-5 мин/день).
  Расходы только на LLM-токены (ключ пользователя).
- NFR-2 (Приватность). **Не логировать содержимое сообщений и секреты.** На публичном
  репо логи Actions видны всем. Логи — только метрики (число чатов/сообщений, тайминги).
- NFR-3 (Безопасность). session = полный доступ к аккаунту → только в Secret, никогда
  в коде/выводе/коммитах. Деплой-инстанс рекомендуется делать **private**.
- NFR-4 (Простота развёртывания). Настройка через GitHub UI; единственный
  не-UI шаг (логин) выполняется в Codespaces, без локального тулчейна.
- NFR-5 (Надёжность). Обрабатывать `FLOOD_WAIT` Telegram (middleware авто-retry).
- NFR-6 (Без состояния/БД). Единственное персистентное состояние — session в Secret.
  Пиры резолвятся каждый запуск; апдейты не слушаются; сообщения не хранятся.
- NFR-7 (Сопровождаемость). Структура по мотивам `ardanlabs/service` (слои
  foundation/business/app, бинарники в `api/cmd/*`), упрощённая под CLI-cron.

## 5. Ограничения и допущения

- C-1. MTProto требует `api_id` + `api_hash` с my.telegram.org (свои у каждого Deployer).
- C-2. Логин интерактивен (код из Telegram) — полностью «в один клик» невозможно;
  минимизируем через Codespaces.
- C-3. cron в GitHub Actions — «best-effort» (возможна задержка); для суточного
  дайджеста приемлемо. Scheduled workflow отключается после 60 дней без активности репо.
- C-4. IP раннеров Actions меняется → Telegram может слать «новый вход»; риск умеренный
  (переиспользуется уже авторизованная сессия).
- C-5. `ardanlabs/conf` + yaml игнорирует нулевые значения → content-конфиг читаем
  обычным `gopkg.in/yaml.v3`, секреты — через conf (env).

## 6. Вне scope (v1)

- Прочие LLM-провайдеры (только интерфейс под будущее).
- Веб-интерфейс/дашборд, БД, дедуп по курсорам, реакция на апдейты в реальном времени.
- Скачивание/анализ медиа (только текст + плейсхолдеры).
- Мультиязычные шаблоны промптов сверх параметра `output_lang`.

## 7. Критерии приёмки

- AC-1. `go build ./...` и `go vet ./...` проходят.
- AC-2. `go run ./api/cmd/login` в Codespaces выдаёт session и кладёт его в Secret.
- AC-3. С валидным session и `config.yml` (1 чат, `window_hours: 2`, `target_chat: me`)
  `go run ./api/cmd/svodka` присылает дайджест в «Saved Messages».
- AC-4. После смены `target_chat` на группу дайджест приходит в группу.
- AC-5. Ручной запуск через `workflow_dispatch` даёт зелёный прогон; в логах нет
  содержимого сообщений и секретов.
